## 1. Purpose and scope

This file answers "what work exists, in what order of value, with what acceptance and what evidence" for the whole project. It covers M0 through M3, every Must and Should requirement of `REQUIREMENTS.md` §5–§11, the process and documentation obligations created by the decision set, and the deferred register.

It does not own: milestone objectives, entry and exit criteria, sequencing constraints or release mechanics (`TECHNICAL_PLAN.md`); readiness and done definitions (`DEFINITION.md` §2, §3); test strategy, IDs and required checks (`TESTING.md`); the commit protocol (`CONTRIBUTING.md`).

## 2. How to read this file

### 2.1 Identifier and column scheme

Every task carries all twelve columns below. A task that genuinely has no requirement (a build, CI, documentation or process obligation) cites the governing `DEC-###` in the Requirements column instead, and says so.

| Column | Meaning |
| --- | --- |
| `ID` | `TASK-###`, zero-padded to three digits. Allocated once, never reused. |
| `Title` | Imperative one-line statement of the outcome. |
| `Type` | `Product` (user-visible behaviour) · `Tech` (architecture, build, platform, CI, tooling) · `Doc` (documentation) · `Test` (verification infrastructure or verification work) · `Risk` (risk treatment and register work). |
| `Milestone` | `M0` repository and documentation baseline · `M1` Android · `M2` iOS · `M3` hardening and release. Objectives per milestone are in `TECHNICAL_PLAN.md` §2. |
| `Block` | The execution block that groups the task for simultaneous delivery (`B1`…`B9`, §2.6), or `—` for a task outside the block plan. The column is an execution grouping; `Milestone` remains the delivery grouping. `TASK-014`…`TASK-016` read `Done`, because they were executed individually before the block model. |
| `Value` | Why the task exists — the review, requirement or decision it serves. |
| `Requirements` | The `REQ-*` ids the task delivers, or the governing `DEC-###` when no requirement applies. |
| `Dependencies` | Prerequisite `TASK-###` ids. The chain is enforced by `TECHNICAL_PLAN.md` §5. |
| `Priority` | MoSCoW-aligned, consistent with the requirement's own priority in `REQUIREMENTS.md`: `Must` (MVP), `Should` (committed for the deliverable), `Could` (deferred, see §6). |
| `Size` | `S` · `M` · `L`, defined in §2.2. |
| `Acceptance` | The `AC-…` ids from `REQUIREMENTS.md` that the task must satisfy, or — where no criterion exists yet — one observable outcome. Existing criteria are cited, never restated. |
| `Expected tests` | The `TEST-…` ids from `TESTING.md` §16 that will carry the evidence, or `—` with a reason for tasks whose evidence is a gate artefact rather than a test. |
| `Status` | `Proposed` · `Ready` · `In progress` · `In review` · `Done`. Mirrors the GitHub Issue state (DEC-044). |

Two rules apply to every row:

- **TDD is the unit of progress** (DEC-053). A task is not started until its first failing test exists and its red run has been observed; where the row's Expected-tests cell names several ids, one red/green cycle per behaviour increment is expected. The recognised exceptions — pure documentation, build/CI configuration, tooling — are stated in the row's Acceptance cell and are the only ones allowed.
- **The full required check set is mandatory on every pull request** (DEC-054). The check list is owned by `TESTING.md` §14; the gate is owned by `DEFINITION.md` §3. `Done` here means the pull request's final state was green on both platform runners.

### 2.2 Sizing

Sizes describe review load, not effort estimates, and they exist so a task is small enough to be reviewed in one pass.

| Size | Definition |
| --- | --- |
| `S` | One module, a small number of files, no new contract; completable and reviewable in a single review cycle. |
| `M` | Several files across one or two modules; adds tests or wiring, but introduces no new cross-module contract. |
| `L` | Spans multiple modules or both platforms, or introduces a new contract, build capability or CI pipeline; needs its own sequencing and cannot land in a single review cycle. |

### 2.3 Definition of Ready

A task stays `Proposed` until `DEFINITION.md` §2 is satisfied for it. That checklist — requirement and acceptance criterion exist, dependencies named, size assigned, impacted documents identified, test intent known, no blocking decision unresolved, not deferred, design reference present for UI work, contract present for data work — is owned there and is not restated here. A task that cannot meet a mandatory item MUST NOT be started "partially" to discover the missing input.
